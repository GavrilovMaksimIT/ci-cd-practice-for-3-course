# Практическая работа для допуска к выполнению КТ3 для групп 24.1, 24.2, 24.3

Цель: проследить путь изменения от коммита до результата автоматической проверки.

## Исходные требования

- Необходим аккаунт GitHub и доступ к учебному репозиторию.
- Готовый проект из папки `demo` и файл `workflow_templates/ci.yml.txt`. Внимание! Сначала нам нужен именно .txt файл
- Приложение и тесты писать не нужно. Тесты в этой практике не изменяем.

## Что сделать

1. Создайте **отдельный публичный учебный** репозиторий `cicd-first-run` с README и веткой `main`. Если создаётся другая ветка, переименуйте её в `main` до настройки workflow.
2. Загрузите `site/`, `tests/`, `build.py` из `demo` в корень. Папки должны сохранить структуру. Если браузер не принимает папки, используйте Add file → Create new file и создайте каждый файл по полному пути. Не загружайте ZIP вместо его содержимого.
3. Через Add file → Create new file создайте `.github/workflows/ci.yml`. Вставьте **всё содержимое** `workflow_templates/ci.yml.txt`, сохраните коммит в `main`. Файл содержит отступы пробелами, не табуляцией.
4. Откройте Actions → Lesson CI → последний запуск → check-build. Найдите Run tests, четыре успешных теста и следующий шаг Build site. Дождитесь завершения всего запуска.
5. На странице запуска найдите артефакт `lesson-site`, скачайте и распакуйте его. Откройте `index.html`. В `release.json` найдите коммит исходников. Скачивание артефакта — ещё не публикация сайта в интернете.
6. В `site/index.html` замените только `href="style.css"` на `href="missing.css"`. **Перед сохранением** запишите прогноз: какой тест упадёт и какие последующие шаги не выполнятся. В Run tests найдите название упавшего теста и строку с причиной ошибки.
7. Найдите соответствующий красный запуск. В Run tests найдите `test_stylesheet_exists` и `Missing stylesheet: missing.css`. Проверьте статус Build site и Save site artifact.
8. Верните `href="style.css"`, сохраните новый коммит `restore stylesheet link` в `main`. Убедитесь, что новый запуск зелёный. Старый красный запуск останется красным — это история проверки другой версии.
9. В **другом** коммите измените `Аудитория: 301` на `Аудитория: 302`. Предскажите результат тестов, проверьте его. Объясните, почему эти проверки не доказывают правильность номера аудитории.

## Что сдать

Создайте `report.md` в репозитории. В нём укажите:

- Ссылки на один красный и один исправленный зелёный запуск, коммиты этих запусков.
- Прогноз до поломки и фактический результат.
- Название упавшего теста и строку причины из журнала.
- Что произошло с шагами сборки и сохранения артефакта после ошибки.
- Где выполнялись тесты и почему результат сохранён на GitHub, а не только у вас на компьютере.
- Почему зелёный результат после смены аудитории не доказывает отсутствие ошибки.

Сдача отчёта тоже создаст запуск: workflow настроен на каждый push в `main`. Выбирайте запуски по коммитам, а не только по положению в списке.

## Критерии проверки для выставления статуса "сдано" на платформе и успешного допуска к КТ3

- workflow находится в правильном месте и зелёный запуск;
- воспроизводимая поломка и указана её причина;
- отдельное исправление и успешный повторный запуск;
- объяснены runner, остановка последующих шагов и артефакт;
- сделан вывод об ограниченности проверок.
